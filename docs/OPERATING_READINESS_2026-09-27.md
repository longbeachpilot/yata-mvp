# YA TA 첫 고객 운영 준비

기준: 2026-09-27. 실제 교육 제공 학원 미확보, 법인 설립·사업자등록 진행 중, 이메일 문의만 운영. 이 문서는 준비 상태이며 공개 영업 완료 선언이 아니다.

## 이번에 구현한 기능

- 학습자·교관 예약 화면: 화면이 보이는 동안 30초마다 재조회, 탭으로 돌아오면 재조회, 수동 새로고침 및 마지막 성공 시각 표시. 네트워크 오류를 빈 예약 목록으로 표시하지 않는다.
- 예약 이력: 요청·확정·완료·취소를 DB 트리거로 기록. 본인 예약의 학습자·교관 및 관리자만 조회 가능. 설치 이전 예약은 당시 상태를 `baseline`으로 기록하며 과거 발생 시각을 추정하지 않는다.
- `/admin/bookings`: 관리자에게만 고객·교관 이메일, 상태, 안내 기록 표시. 목록 50건 단위, 필터 및 페이지 이동. 일반 계정은 관리자 RPC가 거절하며 화면에서도 연락처를 지운다.
- 이메일 초안 버튼은 메일 앱을 연다. 자동 발송 기능이 아니다. 운영자가 실제 발송 후 확인 대화상자를 거쳐 안내 사실을 수동 기록한다. 수신 확인은 지원하지 않는다.
- 상태 변경 시 새 안내가 필요하다. 이전 상태를 보고 안내한 사이 예약이 바뀌면 기록을 거절한다. 같은 상태·대상에 대한 중복 기록은 추가되지 않는다.
- 교관은 확정 예약도 취소할 수 있다. 안내 및 별도 환불 처리를 요구하는 확인 문구가 표시된다.
- 저장된 Logbook을 다시 열면 기존 코멘트·목표를 확인하며 중복 작성 화면으로 돌아가지 않는다.
- 회원가입 메일 발송 한도 오류를 한국어로 안내하고 고객 문의로 연결한다.

## 첫 고객 운영 순서

1. 검증된 제휴 학원만 공개한다. 현재 등록 프로필과 보험 플래그만으로 실제 등록·보험 확인이 완료됐다고 판단하지 않는다. 관리자 교관 공개 버튼을 누르기 전 자료를 확인한다.
2. 확정 가능한 미래 일정과 최종 수업료를 등록한다. 학원명·직접 결제 방법·포함 수업 범위·취소 조건을 고객에게 전달한다.
3. 운영자는 예약 운영 화면에서 요청을 확인하고 교관에게 메일을 보낸다. 실제 발송 후 교관 안내를 기록한다. 교관이 대시보드에서 확정해야 예약 상태가 바뀐다.
4. 확정 상태에서 고객과 교관 모두에게 일정·만남 장소·교육 제공 학원·금액·취소 조건을 안내한다. 실제 발송 후 각 안내 기록을 남긴다. 상태를 바꾸는 것만으로 상대에게 이메일이 가지 않는다.
5. 수업 종료 후 교관이 실제 수업 이행 여부를 확인하고 완료 처리한다. 예정 종료 시간 전에는 UI와 DB 모두 완료를 막는다. 예정 시간이 지났다는 사실만으로 수업 이행이 자동 확인되지는 않는다.
6. 교관이 Logbook을 작성한다. 고객은 내 수업에서 Logbook을 읽고 완료된 수업에 후기를 한 번 작성한다.
7. 운영자는 고객의 수업·후기 완료를 확인하고 취소·환불·분쟁 미처리 건이 없는지 확인한다.

## 장애·취소 대응

- 고객/교관은 해당 예약의 ‘이 예약 문의’ 버튼을 사용한다. 운영자는 예약번호로 관리자 목록과 변경 이력을 대조한다.
- 결제하지 않은 예약도 취소 상태를 양쪽에 안내한다. 이미 학원에 결제했다면 환불 담당자·처리 결과를 별도로 확인한다. 앱에서 취소 또는 안내 기록이 있어도 환불 완료를 뜻하지 않는다.
- 통신 오류 뒤 저장 결과가 불확실하면 다시 제출하기 전에 새로고침한다. 이력과 현재 상태를 함께 확인한다.
- 자격 확인 자료·신분증·면허증·인증번호·비밀번호를 일반 문의 메일로 받지 않는다. 전용 확인 절차가 정해지기 전 실물 자료 수집을 시작하지 않는다.

## 검증 범위

- `npm run check`: 시간 경계/리다이렉트/지역 매칭 단위검사, TypeScript, production build.
- `tests/database-booking-completion.sql`: 실제 DB RPC의 시간·소유권·중복 예약·취소 규칙. 한 트랜잭션으로 실행 후 ROLLBACK.
- `tests/database-booking-operations.sql`: 관리자 권한, 이력 소유권, 연락 기록의 멱등성/변경 충돌, 완료 전 후기 차단, 수업 기록과 6개 숙련도 조회, 중복 기록·후기 차단. 실제 DB에서 통과. 테스트 후 예약 5건·관리자 1명 유지, 테스트 사용자 0건 확인.
- `npm run test:browser`: GitHub Actions에서 Chromium으로 390px 모바일 및 관리자 1440px 검사. 외부 API는 가상 응답으로 격리한다. 실제 회원가입, 이메일 발송, 실결제, 실제 수업 이행을 검증하지 않는다. 첫 실행 [Quality #147](https://github.com/longbeachpilot/yata-mvp/actions/runs/36284267826)에서 전체 흐름을 통과했다. 6개 모바일/데스크톱 스크린샷을 CI artifact로 저장했다. 이후 실행 결과는 해당 커밋의 Quality workflow에서 확인한다.
- 실제 두 계정과 실제 휴대폰을 사용한 인증메일→예약→확정→수업→후기 리허설은 별도 남아 있다. 현 환경에서 로컬 브라우저 실행 파일이 손상되어 CI 브라우저로 검사한다.

## DB/보안 운영 주의

변경 이력은 `yata_private.booking_events`에 보관한다. 직접 읽기·쓰기 권한이 없으며 관리자 여부 또는 예약 당사자 여부를 검사하는 RPC만 실행한다. 기존 기록을 삭제하는 migration은 포함하지 않는다.

Supabase Advisor의 private 테이블 RLS 정책 없음 및 인증 사용자용 SECURITY DEFINER 경고는 의도된 RPC 접근 설계를 검토했다. 새 RPC의 비관리자 거절과 타인 이력 차단을 테스트했다. 이것은 전체 보안감사 인증이 아니다. 유출 비밀번호 보호 비활성화 경고는 별도 남아 있다.

- [RLS 정책 없음 설명](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)
- [SECURITY DEFINER 노출 점검](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable)
- [유출 비밀번호 보호](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)

이번 이력 migration 및 직전 완료시간 migration 파일명은 원격 적용 버전(`20260927005134`, `20260927001121`)과 맞췄다. 기존 원격 스키마 전체가 로컬 migration으로 재현되는지는 별도 검증이 필요하다. 테스트 데이터 ROLLBACK 검사는 백업 복원 훈련을 대체하지 않는다. 백업 보존/복구 방법을 운영 전에 확인하고 실제 개인정보 포함 백업 파일을 공개 저장소에 넣지 않는다.
